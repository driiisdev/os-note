# Practice: Hello, Three Ways

Concept note: [`os-intro.md`](<../../../concepts/os into/os-intro.md>)

## What this demonstrates

That a user program has exactly **one** way to make the hardware do anything: ask the kernel,
through a **system call**. `printf`, `write()` and a hand-written `syscall` instruction look
like three different things - this project shows they all end at the same kernel doorway.

It also includes a short tour (`sysinfo.sh`) of the hardware the OS is managing, read from the
virtual files the kernel exposes in `/proc` and `/sys` - the "system architecture overview"
part of the section, seen from the machine you're actually on.

## Folder structure

```text
hello-three-ways/
  hello.c       <- printf vs write() vs a raw `syscall` instruction (inline assembly)
  sysinfo.sh    <- CPU, caches, memory, disks, NICs, interrupts - straight from /proc and /sys
  Makefile      <- `make`, `make trace` (needs strace)
```

## Build & run

```bash
make
./bin/hello              # all three
./bin/hello raw          # just one: printf | write | raw
bash sysinfo.sh
make trace               # sudo apt install strace first
```

## What you'll actually see

```text
$ ./bin/hello
1) hello via printf()  - libc formats + buffers, then calls write()
2) hello via write()   - thin libc wrapper around the syscall
3) hello via syscall   - raw instruction, no libc in the path
```

## Code walkthrough

The raw version does by hand what libc's `write()` wrapper does for you:

```c
__asm__ volatile("syscall"
                 : "=a"(ret)                                   // result comes back in rax
                 : "a"((long)SYS_write), "D"((long)fd),        // rax = syscall number (1)
                   "S"(buf), "d"(len)                          // rdi, rsi, rdx = arguments
                 : "rcx", "r11", "memory");                    // the CPU overwrites rcx/r11
```

- **rax** holds the syscall number - `SYS_write` is 1 on x86-64 Linux.
- **rdi, rsi, rdx** hold the first three arguments - that's the Linux x86-64 syscall ABI.
- The **`syscall` instruction** switches the CPU into kernel mode and jumps to the kernel's
  entry point; `sysret` brings it back. Everything in between is the kernel's code.

`printf` adds two layers on top: formatting (turning `%d` into digits) and **buffering** - it
collects output in user memory and only calls `write()` when the buffer fills, on a newline
(for terminals), or on `fflush`. That's why `hello.c` calls `fflush(stdout)` - without it,
piping the output (`./bin/hello | cat`) would print line 1 *last*, since the pipe makes stdout
fully buffered and the raw writes would overtake it.

## Try this yourself

- Remove the `fflush(stdout)` and run `./bin/hello | cat` - watch the order change.
- Change `SYS_write` to `SYS_getpid` (no arguments needed) in a copy of `raw_write`, and return
  your PID without ever calling libc's `getpid()`.
- `ls /proc/self/` - every file there is generated by the kernel on the spot, describing the
  `ls` process itself.

## Real-world equivalent

Every language runtime - Go, Rust's std, Node's libuv, the JVM - ends at this same instruction.
Go famously makes raw syscalls itself on Linux instead of going through libc. Tools like
`strace`, `ltrace` and eBPF-based tracers work precisely because the syscall boundary is the
one narrow place where all of a program's interaction with the outside world passes through.
