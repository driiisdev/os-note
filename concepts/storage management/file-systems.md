# File Systems

A storage device is a giant numbered array of blocks. A **file system** is the data structure,
stored *on* those blocks, that turns them into named files in a tree of directories - and keeps
that structure consistent when the power fails halfway through an update.

## The building blocks (Unix-style file systems: ext2/3/4, and the same ideas in most others)

```text
 +------------+--------------+--------------+---------------+---------------------------+
 | superblock | inode bitmap | block bitmap |  inode table  |        data blocks        |
 +------------+--------------+--------------+---------------+---------------------------+
   what FS,     which inodes   which data     one fixed-size   file contents and
   sizes, where are in use     blocks are     record per file  directory contents
   regions are                 in use
```

| Structure | What it holds |
| --- | --- |
| **Superblock** | file system type, block size, counts, where each region starts, state (clean/dirty) |
| **Bitmaps** (or free lists / B-trees) | which inodes and blocks are free |
| **Inode** | everything about a file **except its name**: type, size, permissions, owner, timestamps, link count, and **where its data blocks are** |
| **Data blocks** | file contents - and, for directories, the directory's entries |
| **Directory** | a special file containing `(name → inode number)` entries |

### Where a file's data is: block pointers vs extents

- **ext2/ext3**: 12 **direct** block pointers in the inode, then **single, double and triple
  indirect** blocks (blocks full of block numbers) for bigger files.
- **ext4, XFS, NTFS, APFS**: **extents** - "blocks 5000-5999" as one entry - far more compact for
  large contiguous files.

### Names live in directories, not in files

```text
 /home/ada/notes.txt

 inode 2 (root dir)      ->  entries: ".":2  "..":2  "home":131
 inode 131 (home)        ->  entries: "ada":4012
 inode 4012 (ada)        ->  entries: "notes.txt":9001
 inode 9001 (the file)   ->  size 2.1KB, mode 0644, blocks [88231]
```

Opening a path means **resolving** it component by component: read each directory, find the next
name, follow its inode number. The kernel caches results (the **dentry cache**) so this is fast
the second time.

Consequences of this design:

- **Hard links**: two directory entries pointing to the same inode. The inode's **link count**
  tracks how many names it has; data is freed only when the count reaches 0 *and* no process has
  it open. That's why the syscall is `unlink()`.
- **Symbolic links**: a tiny file whose content is a *path* - it can point anywhere, even to
  nothing.
- **`mv` within one file system is instant** regardless of file size - it only edits directory
  entries.
- **You can run out of inodes** before running out of space (millions of tiny files): `df -i`.

## Crash consistency

Creating one file touches several structures: the inode bitmap, the inode, the block bitmap,
a data block, and the parent directory. A crash in the middle can leave them inconsistent - a
directory entry pointing at a free inode, or an allocated block nobody owns.

| Approach | How | Used by |
| --- | --- | --- |
| **fsck** | scan the whole disk after a crash and repair | ext2, FAT - slow on big disks |
| **Journaling** | write the intended changes to a **journal** first, commit, then apply; replay after a crash | ext3/ext4, XFS, NTFS |
| **Copy-on-write** | never overwrite in place; write new versions elsewhere, then atomically switch a root pointer | btrfs, ZFS, APFS |
| **Log-structured** | the whole file system is an append-only log | F2FS (flash), LFS |

ext4's default `data=ordered` mode journals **metadata** only, but forces file data to be
written before the metadata that points to it is committed.

## The VFS: one interface, many file systems

Linux's **Virtual File System** layer gives every file system the same operations (`open`,
`read`, `write`, `stat`, `readdir`, `mmap`...). That's why `cat` works the same on ext4, a USB
stick (FAT), an NFS share, `/proc` (generated by the kernel) or `tmpfs` (RAM-only).

```text
 process: fd 3 --> [open file description: offset, flags] --> [inode] --> file system
                   (shared after fork / dup)
```

## Clarifications

- **A directory is just a file** with a special format - which is why "everything is a file" works.
- **Deleting a file you have open doesn't free its space** until you close it - a classic cause
  of "the disk is full but `du` says it's empty" (`lsof +L1` finds them).
- **Block size ≠ sector size ≠ page size** (often all 4KB today, but they're three different
  layers).
